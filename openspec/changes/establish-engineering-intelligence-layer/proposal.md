# Proposal: Engineering Intelligence Layer v0.2

## Intent

Современные coding-агенты способны писать код, но успех разового изменения не равен снижению стоимости развития проекта. Не хватает воспроизводимой инженерной политики, evidence-based приёмки и сравнений качества на **последовательных изменениях**. Нужно обеспечить внешний слой, который одинаково применим к различным движкам и измеримо снижает дефекты и стоимость корректных изменений.

## Product thesis

**Every build must make the next build easier** — проверяемая гипотеза, не гарантированное свойство. EIL должен обеспечивать измерение стоимости эволюции и предотвращение архитектурной деградации.

## Capabilities in scope

1. CLI `eil check` для проверки уже существующего diff независимо от агента.
2. Контракт задачи, охватывающий scope, acceptance, risk, allowed changes, protected files.
3. Детерминированные gates: typecheck, tests, lint, архитектурные границы, API compatibility, lockfile delta, DS rules при наличии.
4. Локальные контекстные инструменты `symbols`, `references`, `impact` для JS/TS; без обязательного постоянного Code Graph.
5. Адаптер Pi SDK, запуск в разрешённом рабочем каталоге с явной политикой инструментов.
6. Изолированное исполнение на отдельной копии репозитория и worktree, ограниченные права, запрет сетевых/секретных действий по умолчанию.
7. Task ledger в SQLite: модели, попытки, затраты, проверки, принятие человеком, регрессии.
8. Risk-aware two-tier cascade: дешёвая попытка для low/medium; сильная модель сразу для high-risk только с независимой проверкой.
9. A/B/C benchmark на одном и том же engine, затем 6+ последовательных изменений.
10. Вывод evidence bundle (diff, результаты проверок, стоимость, причины отказа) для ревью.

## Out of scope

- Собственный полноценный coding agent, автономный планировщик или постоянный swarm.
- Визуальный редактор, генератор full-stack приложений, облачная SaaS-платформа.
- Neo4j, глобальный код-граф по нескольким репозиториям, UI schema runtime.
- Поддержка множества agent SDK одновременно в первой реализации.
- Зависимость от LiteLLM или OpenCode.
- Fine-tuning, decision-модели Jev/ONNX или online bandit в v0.2.
- Автоматический merge, write-to-main, продакшен-развёртывание.

## Intended users

Разработчик/техлид, работающий с существующим TypeScript/React репозиторием и желающий получить управляемые изменения; позже — продуктовые и дизайн-команды, которым нужна Design System Native сборка.

## Measurable validation

Главное сравнение: A = базовый coding-agent; B = тот же engine/model + Engineering Gates; C = B + risk-aware routing/evaluation. Сравнение производится по accepted cost, functional correctness, human review time, regression tax и последовательным изменениям при идентичном исходном Git commit и требованиях.

## Risks

- Проверки могут иметь ложноположительные результаты и вредить скорости.
- Не все регрессии обнаруживаются тестами; `tests pass` ≠ `accepted`.
- Стоимость человеческого ревью сложно измерить без согласованных правил.
- Низкая статистическая мощность на малом числе задач.
- Модель и engine взаимодействуют: сравнивать нужно в парных условиях.
- Работа с корпоративным кодом требует явного разрешения на внешние model APIs.

## Success condition for proceeding beyond MVP

Не фиксировать заранее численные обещания экономии. Система должна устойчиво выполнять обязательные gates, создавать полный audit trail и хотя бы не ухудшать качество относительно baseline. Для вывода о выгоде нужны доверительные интервалы и повторяемые задачи, а не отдельный демонстрационный успех.
