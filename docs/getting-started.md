# EIL для начинающих: пошаговая инструкция с нуля

## Совсем некогда читать? Одна команда, ноль файлов

Проверка уже готового диффа работает **без всяких конфигов** — прямо в
папке проекта, где есть незакоммиченные изменения:

```bash
node /путь/к/dist/apps/cli/main.js check --repo .
```

Что произойдёт: EIL быстро просмотрит дифф (не запуская ничего на вашем
компьютере) и напечатает вердикт. Три исхода:
- `needs_review (exit 0)` — всё чисто, дальше решает человек;
- `blocked (exit 1)` — в диффе что-то плохое (секрет, файлы вне границ,
  спрятанные изменения) — написано что именно;
- рядом появится папка `eil-evidence/…` с человеческим отчётом `summary.md`.

Хотите больше (запуск тестов, свои границы) — читайте дальше, это два
небольших YAML-файла.

---

Это практическое руководство. Каждая команда ниже проверена живым прогоном;
выводы в примерах — реальные. Пять минут от «склонировал» до «понял, как
пользоваться».

---

## Что это вообще такое (30 секунд)

`eil` — это **судья для диффов**, а не ещё один кодинг-агент. Вы (или
какой-то AI-агент) делаете изменение в git-репозитории — EIL проверяет дифф
по заранее записанным правилам и выдаёт вердикт с доказательствами:

- **можно ли вообще** такое менять (scope);
- **не утёкли ли секреты**;
- **не сломаны ли** типы/линт/тесты (если вы это разрешите);
- **не спрятаны ли** изменения от git (skip-worktree, вложенные репозитории…).

EIL **никогда** не мержит, не пушит и не «принимает» работу сам: зелёные
гейты означают только «машина не против» — статус `needs_review`, а
принятие работы всегда отдельное человеческое действие.

Наглядно: **агент делает → EIL проверяет → человек решает.**

## Установка (1 минута)

Нужны Node.js ≥ 20 и git ≥ 2.28.

```bash
git clone https://github.com/tvyonix/engineering-intelligence-layer.git
cd engineering-intelligence-layer
npm ci && npm run build
```

Проверка, что всё собралось:

```bash
node dist/apps/cli/main.js --version
# 0.2.0-alpha.4
```

Дальше команды пишутся как `node dist/apps/cli/main.js <команда> …`.
Если надоело длинно — один раз: `npm link`, и всё заработает как просто `eil`.

## Главные два файла

Перед первой проверкой нужны два YAML-файла. **Важно: кладите их ВНЕ
проверяемого репозитория** (например, в соседнюю папку) — иначе EIL увидит
их в диффе как посторонние файлы. Это грабля №1, на которую наступают все.

### 1) `task.yaml` — что разрешено этой задаче

```yaml
version: 1
id: add-multiply                  # латиница, цифры, дефисы; 3–64 символа
baseCommit: "abc1234"             # от какого коммита отсчитываем дифф
description: "Добавить функцию умножения"
scope:
  allow:                          # ГДЕ можно менять (глобы от корня репо)
    - "src/**"
  protect:                        # ЧТО нельзя трогать ни при каких условиях
    - ".env*"
    - ".github/**"
acceptance:
  - id: mul-works
    description: "mul(2,3) === 6"
policy:
  maxAttempts: 2
  noNewDependencies: true         # package.json/lockfile менять нельзя
```

### 2) `policy.yaml` — что и как проверять (файл оператора)

Минимальная политика для старта — только статические проверки, ничего не
запускает на вашем компьютере:

```yaml
version: 1
quality:
  required:
    - "path-scope"      # дифф внутри allow и не трогает protect
    - "secrets-scan"    # в изменениях нет ключей/токенов
```

Если `--policy` не передать, включится политика по умолчанию: `path-scope,
dependency-policy, secrets-scan, types, lint, tests`. Но `types/lint/tests`
требуют запускать команды репозитория, а EIL **по умолчанию ничего не
запускает** — это грабля №2: без явного разрешения эти гейты дадут `error`
(`execution_not_permitted`), и вердикт будет `error` (exit 2). Это не баг,
это безопасность: чужой репозиторий мог бы подсунуть что угодно в `npm test`.

## Сценарий 1 — проверить готовый дифф (основной, 90% случаев)

Ситуация: в репозитории уже есть незакоммиченные изменения (сделал агент
или человек), и вы хотите понять: «это вообще можно принимать?».

```bash
# 1) в репозитории с изменениями смотрим текущий коммит
cd ~/work/widget
git rev-parse HEAD          # например 6216936 — это пойдёт в baseCommit

# 2) рядом (ВНЕ репо) описываем задачу и политику — файлы выше

# 3) запускаем проверку
node /path/to/dist/apps/cli/main.js check \
  --repo . \
  --task ../task.yaml \
  --policy ../policy-min.yaml \
  --out ../evidence
```

Реальный вывод этого прогона:

```text
EIL check summary
-----------------
  path-scope           pass           mandatory all changed paths are within the allow scope…
  secrets-scan         pass           mandatory scanned 1 file(s)…

verdict: needs_review (exit 0); risk: low
all mandatory gates passed; human review is required — EIL never merges
evidence: /tmp/eil-guide-Mdeo/ev2 (summary: summary.md, bundle: evidence.json, task record: task-record.md)
```

### Как читать вердикт

| verdict | exit code | смысл |
|---|---|---|
| `needs_review` | 0 | Все обязательные гейты зелёные. Машина не против — дальше решает человек. |
| `blocked` | 1 | Обязательный гейт упал (вылезли за scope / секрет в диффе / спрятанные изменения). Принимать нельзя, чинить. |
| `error` | 2 | Проверка не завершилась (нет разрешения на запуск команд, git сломался, гейт неизвестен). Пропуск проверки ≠ успех. |

Рядом всегда есть `risk: low/medium/high/blocked` — детерминированная
оценка (auth/крипто/CI-файлы → high и т.п.). Риск — это «сколько внимания
нужно человеку», а не вердикт.

### Где результаты

Всё лежит в папке `--out`:

- `summary.md` — сводка для чтения глазами;
- `evidence.json` — машиночитаемый бандл (все гейты, нарушения, риск);
- `task-record.md` — запись о задаче: критерии приёмки, вердикт, «not accepted»;
- `logs/` — полные логи каждого гейта и сам дифф (секреты в нём замаскированы).

### PR-отчёт одной командой

```bash
node …/main.js report --evidence ../evidence --out ../pr-comment.md
```

Даёт самодостаточный markdown без абсолютных путей — можно вставить в PR.

## Сценарий 2 — включить запуск тестов/линта (когда доверяете репозиторию)

EIL запустит команды репозитория **только** в репозиториях, которые вы
лично внесли в белый список, и только команды, которые вы сами прописали:

```yaml
# policy-full.yaml
version: 1
quality:
  required:
    - "path-scope"
    - "secrets-scan"
    - "dependency-policy"
    - "types"
    - "lint"
    - "tests"
  commands:                       # ЯВНЫЕ команды (по умолчанию — npx-заглушки)
    types: "npx --no-install tsc --noEmit --pretty false"
    lint: "npx --no-install eslint . --format json"
    tests: "npm test"
execution:
  vettedRepos:                    # realpath ЛИЧНО проверенных вами репозиториев
    - "/Users/you/work/widget"
  timeoutMs: 120000
```

`realpath` — буквально: выполните `realpath /Users/you/work/widget` и
вставьте вывод (на macOS `/var` → `/private/var` — частая причина «я
указал путь, а оно не работает»).

Теперь `types/lint/tests` реально выполнятся. Провал тестов → `blocked`.
Новые нарушения линта отличаются от старых: унаследованные не валят
вердикт, только новые.

## Сценарий 3 — прогнать «движок» под надзором (`eil run`)

Это полный конвейер: изолированный клон → ваш скрипт-«движок» правит код →
EIL проверяет дифф → при провале автоматический ретрай → всё в журнал.

В политике из сценария 2 добавьте:

```yaml
execution:
  vettedRepos: ["/Users/you/work/widget"]
  engineCommand: 'bash ~/work/widget/apply-change.sh {attempt}'
  maxCheapRetries: 1
```

Запуск:

```bash
node …/main.js run --repo ~/work/widget \
  --task ../task.yaml --policy ../policy-full.yaml \
  --out ../run-out --ledger ../eil.db
```

Каждая попытка: свежий клон, выполнение команды, полный `eil check`
результата, и так до успеха (→ `needs_review`) или исчерпания попыток.
Репозиторий-оригинал не изменяется никогда.

## Сценарий 4 — журнал, приёмка, метрики

```bash
D="node …/dist/apps/cli/main.js"

# журнал (SQLite) можно вести с самого начала: add --ledger к check/run
$D ledger --db eil.db init          # создать/мигрировать

# ЧЕЛОВЕЧЕСКАЯ приёмка — только после needs_review!
$D accept --db eil.db --task add-multiply \
  --reviewer "human:yaroslav" --duration-seconds 300
# → status: accepted  (blocked-задачу accept отвергнет — это защита)

# или отклонить:
$D accept --db eil.db --task add-multiply --rejected --changes-requested "переделать"

# метрики (честные: без данных пишут UNAVAILABLE, а не 0)
$D metrics --db eil.db --markdown

# выгрузка сырых таблиц для анализа
$D ledger --db eil.db export --out ./export
```

## Сценарий 5 — «кто использует эту функцию?» (контекстные инструменты)

Полезно и людям, и агентам — читать-only, ничего не запускают:

```bash
# какие функции/типы живут в файле
$D symbols --repo ~/work/widget --file src/calc.ts
# → [{name: add, kind: function, exported: true, …}, {name: mul, …}]

# где объявлен символ и все его использования (файл:строка:колонка)
$D references --repo ~/work/widget --file src/calc.ts --name add

# что задело изменение: изменённые файлы → затронутые файлы и тесты
$D impact --repo ~/work/widget --base HEAD~1
```

`impact` честно предупреждает, что не видит динамические импорты — в
выводе это помечено явно.

## Шпаргалка по гейтам

| Гейт | Что делает | Запускает команды? |
|---|---|---|
| `path-scope` | дифф внутри `allow`, не трогает `protect` + детект спрятанных изменений (skip-worktree, вложенные git-репо, файлы под exclude) | нет |
| `secrets-scan` | секретообразный контент в изменённых файлах (значения маскируются) | нет |
| `dependency-policy` | изменение package.json/lockfile без одобрения | нет |
| `import-boundaries` | запрещённые импорты и НОВЫЕ циклы (старые — наследие, не валят) | нет |
| `api-compat` | удаление/смена публичного API TS-пакетов | нет |
| `ds-conformance` | правила дизайн-системы (если настроена) | нет |
| `types` / `lint` / `tests` | реальные проверки | **да** (нужен vetted + команды) |

## Частые ошибки

| Симптом | Причина и лечение |
|---|---|
| `outside-allow:task.yaml` | Конфиги лежат внутри репо → перенесите `task.yaml`/`policy.yaml` наружу. |
| `execution_not_permitted` на types/lint/tests | Так и задумано: добавьте репозиторий в `execution.vettedRepos` (realpath!) и пропишите `commands`, либо уберите эти гейты из `required`. |
| «указал репо в vettedRepos, всё равно не пускает» | Путь должен быть результатом `realpath` (macOS: `/private/var/...`). |
| Верджикт `error` | Проверка не дошла до конца — читайте reason у гейта, там всегда конкретика. Пропуск ≠ успех. |
| `zsh: command not found: eil` | Это `npm link` не сделан — вызывайте через `node dist/apps/cli/main.js …`. |

---

## Три принципа, которые стоит запомнить

1. **Зелёный ≠ принято.** `needs_review` означает «машинные проверки
   пройдены»; принятие — это всегда отдельный `eil accept` человеком.
2. **Пропуск ≠ успех.** Любой непроверенный обязательный пункт даёт `error`
   и exit 2, а не тихий успех.
3. **Ничего не исполняется без вашего разрешения.** Чужой репозиторий не
   может заставить EIL запустить команду — только политика оператора может.
